This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
swift build                          # debug build
swift test                           # full suite (swift-testing, ~260 tests, sub-second after build)
swift test --filter "TreeActions"    # one suite; also --filter "SuiteName/testFunctionName"
./scripts/package-release.sh         # release .app bundle + zip → dist/ (version from DirWiz/Info.plist)
.build/debug/dirwiz-cli scan <path> [--json] [--min-size N] [--max-depth N] [-q]
.build/debug/dirwiz-cli duplicates|info|benchmark|snapshot|diff <path>
```

CI (`.github/workflows/ci.yml`) runs `swift build` + `swift test` on `macos-15` for pushes to master and PRs.

Release script notes: signs with the first local Apple identity found, else ad-hoc (`DIRWIZ_CODESIGN_IDENTITY` overrides; `DIRWIZ_DIST_DIR` overrides output dir). Grant Full Disk Access to the installed `/Applications/DirWiz.app`, never to `.build` binaries - ad-hoc rebuilds can lose FDA because macOS ties privacy grants to code identity.

**Local delivery is part of completing user-facing work in Okan's checkout.** After changing app behavior or UI, do not hand off a successful `swift build` while `/Applications/DirWiz.app` still contains older code. After tests pass, run `./scripts/install-local.sh`, then verify the installed/running executable matches the just-built binary. The script builds under `.build/local-app`, records the source commit plus dirty-worktree status in the installed plist, preserves the previous installed app there, and never writes a public artifact to `dist/`. This standing local-build instruction does **not** authorize uploading assets, changing a GitHub release, notarizing, or claiming the local worktree build is the published release; those remain separate release actions.

## Targets and layering

SwiftPM, swift-tools 6.0, **all targets pinned to Swift 5 language mode** (the test target is not pinned and compiles under Swift 6). macOS 15+. Zero external dependencies - keep it that way.

- `Sources/DirWizCore` - scanner, file tree, duplicate/hardlink detection, analyzers, temporal diff, CLI argument parsing. No UI imports.
- `Sources/DirWizUI` - `AppState` + SwiftUI views + Metal cushion treemap.
- `DirWiz/` (app) and `CLI/` (dirwiz-cli) are executable targets. **The test target can only import DirWizCore and DirWizUI** - logic that needs tests must live in DirWizCore, not the executables (pattern: `CLIArguments.swift`, `TemporalDiffSummary.swift`).

## The file tree - core invariants

`FileTree` (Sources/DirWizCore/Scanner/FileNode.swift) is a flat array of packed `FileNode` structs plus a shared string pool. Everything depends on these rules:

- Nodes reference each other by index (`parentIndex`, `firstChildIndex` + `childCount` = one contiguous child slice). Parent index < child index for any real scan.
- Nodes are appended, never removed - **except `removeSubtree`, which compacts the array and renumbers every index**. Any index held across that call is garbage. That is why:
  - `TreeActions.batchTrash(paths:tree:)` re-resolves each path against the current tree immediately before trashing it; the index-based `batchTrash(nodeIndices:)` is only safe for a single index.
  - After any mutating action, `AppState.invalidateAfterTreeMutation()` (AppState+Analysis.swift) is the single reset point: it clears all index-keyed state (search results, recency factors, temporal-diff arrays) and bumps the treemap layout revision via `scanProgress.publishCounters(forceLayoutRevision: true)`. The treemap only relayouts on tree identity / root index / revision changes - forget the bump and it silently renders stale rects with wrong node indices.
- `FileTree` is `@unchecked Sendable` guarded by an internal mutex. Read through `node(at:)`, `nodesSnapshot()`, `pathBuildingSnapshot()` - do not read `.nodes` directly from concurrent contexts.
- Post-scan analyzers walk snapshots via `FileTree.forEachFileInSnapshot` (single blessed walk with a uniform cancellation cadence) and locate nodes by path components via `FileTree.descendPath`. Do not hand-roll a new whole-tree loop in an analyzer.

## Scanner

`getattrlistbulk` raw-buffer parsing with unsafe pointers (`FilesystemProvider.swift`, hot paths in `FileScanner.swift`) - the parser uses FIXED offsets that depend on `FSOPT_PACK_INVAL_ATTRS` packing every requested attribute, so adding/removing a requested attr shifts every later offset (see the offset constants + parsing contract tests). Symlinks are intentionally skipped. Scans also capture `ATTR_FILE_LINKCOUNT` into the `hasMultipleHardlinks` node flag (`FileTree.linkCountsCaptured` marks the flags trustworthy); hardlink groups auto-populate post-scan/post-mutation via `AppState.refreshHardlinkGroups()` - the Hardlinks tab has no run button. The app path defers bundle sizing to a background pass so first paint is fast; the CLI sizes bundles inline. Env knobs: `DIRWIZ_SCAN_WORKERS`, `DIRWIZ_DEFER_TREE`, `DIRWIZ_SKIP_BUNDLE_SIZES`, `DIRWIZ_BUNDLE_WORKERS`, `DIRWIZ_BULK_BUFFER_BYTES`, `DIRWIZ_NO_WARM_START`, `DIRWIZ_NO_EPHEMERAL_DEFER`. Perf landmine: never `reserveCapacity(count + smallDelta)` on a per-directory/per-item path - it defeats Array's amortized growth and turns scanning into O(n²) (masked below the 500k init reservation, brutal above it; use `reserveNodeCapacity`/geometric growth). Scan-time treemap layouts are deliberately sparse + depth-capped (`ScanTimeLayoutBudget`) so live building doesn't starve the scanner.

**Launch & living view** (waves 6-7): `AppState.restoreOnLaunch()` republishes the cached tree instantly at startup (`staleViewAsOf` drives the sidebar badge and keeps the main pane visible while a refresh runs behind it - ContentView gates on `isScanning && staleViewAsOf == nil`); a cold refresh behind a stale view builds a DETACHED tree and swaps at completion, restoring position via `ExplorationCapture` (path-keyed; indices never survive mutations). Session state (expansion/selection/root) persists per volume via `SessionStateStore`. **Living view is auto-apply now** (living-view-auto-apply, reversing plan 037's "decision 3a: no auto-apply, ever"): FSEvents monitoring auto-starts on every scan completion, and `LiveRefreshPolicy` (DirWizCore, pure + clock-injected like `WarmStartPlanner`) decides when accumulated changes splice themselves in via `applyAccumulatedChanges()` - 2s quiescence, 10s minimum interval, 5,000-changed-dir storm threshold (deliberately the SAME value as warm start's `unknownDirectoryCountBackstop`; both are independently pinned to 5,000 by boundary tests). Guards (pause / scanning / heavy task / temporal-diff overlay) outrank the storm signal and never latch - each tick re-decides, so pending changes apply once a guard lifts. The sidebar Live pill names the current reason; there is no Watch Changes button any more. The persistent volume-scan area also has one state-driven control: no displayed tree for the selected volume means `Scan Volume`, a matching displayed tree means `Full Rescan`, and active scan/apply work temporarily owns that same control. Cache-file existence never chooses the label. `SearchView` re-runs its query on `liveRefreshGeneration` because an apply renumbers indices. App cold scans materialize the tree LIVE (immediate mode) - `DIRWIZ_DEFER_TREE` overrides both ways; `ScanProgress` damps early layout bumps until 1,000 files or 20 publishes.

**Warm start** (GUI only; CLI scans stay cold): completed scans persist the tree + FSEvents event id via `TreeCache` (fail-closed binary format - ANY doubt on load returns nil and falls back to a cold scan; any change to `FileNode`'s stored layout MUST bump the cache `formatVersion`). On the next scan, `WarmStart.swift` replays the FSEvents journal since the saved id and `FileScanner.rescanSubtrees` splices only the changed directories into the loaded tree (`removeChildren(of:)` + immediate-mode re-enumeration + `recomputeAggregates()`, which resets non-bundle dir totals then re-sums - never call `propagateSizes()` on an already-propagated tree, it double-counts). Warm-patch admission is governed first by the estimated changed-item fraction (25% of the cached tree by default), then rechecked against exact staged counts after Phase A and before mutation; interactive and trailing tiers consume one shared budget. Root count is only a 512-root sanity backstop, evaluated after the item gate: batched splicing reduced 38 roots from 9.14 s across repeated full-tree compactions to 0.118-0.164 s in one compaction, so root count no longer predicts splice cost. Per-root estimated and actual staged counts are logged for diagnosis. The per-user Darwin temp directory is a permanently changed root holding about 151,600 items and accounted for 42-52% of observed warm-patch work, so `EphemeralPaths` publishes ordinary roots first and sweeps the Darwin `T` and `C` roots in a lower-priority trailing tier; `~/Library/Caches` deliberately stays interactive, and cold scans still enumerate and count all of these roots in full. **Cache-horizon invariant**: while any trailing target remains, do not save `replay.newEventId` or a partially patched tree - leave the previous atomic `TreeCache` untouched, then advance its event id only after the trailing splice completes successfully. Cancellation, quit, or supersession must therefore keep the old cache and replay the whole window next launch; violating this makes deferred staleness permanent and silent. Live monitoring starts before the potentially large cache/history/checkpoint writes so user changes cannot fall into a blind window, and `FSEventsMonitor` filters only DirWiz's own Application Support root so those writes cannot feed another refresh cycle. Poison flags (MustScanSubDirs/IdsWrapped/RootChanged/Mount), replay timeout, unresolvable paths, or >5k changed dirs all abandon warm and run the unchanged cold path. Equivalence tests (`Tests/SubtreeRescanTests.swift`, `Tests/WarmStartTests.swift`, `Tests/DeferredEphemeralWarmStartTests.swift`) pin patched-tree ≡ fresh-cold-scan; keep that gate when touching any of this. **Landmine**: the journal-replay stream MUST create with `kFSEventStreamCreateFlagFileEvents` (matching `FSEventsMonitor`'s live-watch stream) - without it, FSEvents can only report at directory granularity, so any file changing directly inside a huge directory gets blamed on that whole directory. On a root-volume ("/") scan this reliably misreports the entire home folder as "changed" (confirmed live: 76% "changed" from ~8 seconds of ordinary background noise), tripping the changed-item-fraction cold-fallback on nearly every launch. `JournalCollector.handleEvents` reduces file-level events to their parent directory (same as `FSEventsMonitor.processChanges`) so `rescanSubtrees` still receives directory targets.

**Firmlinks defeat the `(dev, inode)` guard** - `VisitedDirectories` cannot dedup them, because the two sides report different identities: `stat /Applications` gives the real inode, but the entry `getattrlistbulk` returns while enumerating `/` carries a synthetic firmlink id (`0x0FFFFFFF00000000 + n`). `dev` is identical on both sides, so a `du -x` mount-crossing rule can't catch them either. Unfixed, this both double-counted (`/Applications` and `/System/Volumes/Data/Applications` each fully enumerated) and stranded content (`/Library` reporting 0 bytes with its real 92.6 GB under the Data path) - and which happened was a worker race, so it varied per run. `FirmlinkTable` parses macOS's own `/usr/share/firmlinks` and seeds `VisitedDirectories` with the Data-side paths to skip; `FileScanner.resolveFirmlinkDuplicates` gates it to scans that span both sides (never when rooted at/below the Data volume) and honors `DIRWIZ_NO_FIRMLINK_DEDUP=1`. It fails open - a missing/malformed table means no dedup, never dropped content. **Both** `scan` and `rescanSubtrees` must use it or the warm-start equivalence gate breaks the moment a firmlinked path changes. Parsing landmine: split lines with `whereSeparator: { $0.isNewline }`, not `split(separator: "\n")` - Swift treats CRLF as one grapheme, so the latter silently merges lines.

**Mount boundaries and firmlinks are complementary, not interchangeable.** An individual volume tree records `MountTraversalScope.selectedVolume`; `VisitedDirectories` then rejects a directory whose device differs from the scan root, leaving the mount point visible but not descending. `combinedVolumes` is selected only through the explicit All Volumes row, while `DIRWIZ_CROSS_MOUNTS=1` resolves to diagnostic `unrestricted`. A missing root device fails open. Every cold, warm, and living rescan must read/write the tree's scope, and TreeCache identity includes it; path `/` alone is not ownership because both individual and combined trees use that root. This device rule cannot catch firmlinks because their duplicate paths share the root device, while `FirmlinkTable` cannot replace the mount rule because arbitrary SSDs, disk images, Update, and Simulator mounts are not firmlinks.

**Why a scan went cold is never silent** (warm-start-observability): every cold-fallback path - `TreeCache.loadResult`'s `.rejected` case (cache existed but failed to load: corrupt/wrong-version/checksum-mismatched - distinct from `.noCacheFile`, "never scanned"), the planner's own `.coldFallback(reason:)`, and `commitWarmStart`'s mid-patch abandonment (unresolved paths / root-level rescan) - threads a human reason into `beginColdScan`'s `coldFallbackReason` param and `lastScanSummary`. Critically, `restoreOnLaunch` (not just `startScan`) also goes through `loadResult`: it runs on every cold launch and is usually the *first and only* code to see a corrupted cache before its own lookup invalidates the file, so if it used the plain `load()` wrapper the reason would be lost forever with nothing left to explain it later. On `.rejected` it does NOT auto-start a scan (today's empty-launch-state behavior is unchanged) but does set `lastScanSummary` via `ScanSummaryComposer.cacheRejectedAtLaunch`. Any new call site touching `TreeCache.load`/`loadResult` for a scan-adjacent decision must keep this discipline - grep for every caller of the shared primitive, not just the already-obvious ones (this is exactly the gap that shipped once already: `restoreOnLaunch` was missed in the original design, caught only by driving it end-to-end in `LaunchRestoreTests.swift`, not just `startScan`).

`WarmStartHistory` (Scanner/WarmStartHistory.swift) persists the last 20 warm/cold decisions per volume as plain JSON - deliberately NOT `TreeCache`'s fail-closed binary discipline; losing this diagnostic history costs nothing, so a malformed file just reads as empty. Recorded at every `lastScanSummary` write site. Reason strings are logged at `.notice` (not `.info`/`.debug` - those two don't persist to the system log store, so `log show` can't retrieve them after the process exits). In this dev environment specifically, bare `log`/`log show` resolve to a zsh shell builtin that silently no-ops - use `/usr/bin/log show`/`/usr/bin/log stream` explicitly, or the "it's not logging" conclusion will be wrong.

## UI state model

`AppState` and its sub-models (`DuplicateState`, `SearchState`, `NavigationState`, `TemporalDiffState`) are all `@MainActor @Observable`. Background work runs in `Task.detached` and hops back via `MainActor.run` guarded by token counters (`scanToken`, `duplicateToken`, …) - always check the token before writing results so a stale task can't clobber a newer scan. `resetForNewScan()` is the canonical list of per-scan state; new state must be added there.

**Treemap render styles** (`Treemap/CardGeometry.swift`): cushion draws hierarchy with *lighting* (parabolic ridges baked into each leaf's coefficients - costs zero pixels, survives extreme density); cards draw it with *geometry* (rounded corners + gaps, bounded by `CardBudget`). One fragment shader branches on `CushionUniforms.styleMode`; `cardSurfaceMode` occupies the final old padding slot, so the uniform stride stays 48 and `verifyCushionLayouts()` still covers it. `FoldersColorScheme` and `FoldersSurfaceStyle` are orthogonal review axes: palette chooses the eight depth hues, while surface chooses frame width, edge weight, expanded-folder chrome, title treatment, and optional bevel. Both styles start from the SAME `SquarifyLayout` output, but Folders then applies surface-aware `CardNesting` while building instances: children move into their parent's padded, header-aware interior. A surface change MUST rebuild instances and publish the new post-nesting `displayRects` to labels and its hit grid together; it never requests a scan or a new Squarify layout. The shader's card gap is a separate concern: it is never subtracted from those hit rects, so card edges and sibling gaps remain clickable (pinned by `CardStyleTests`). Verifying the shader needs an *offscreen Metal render* (`CardStyleRenderTests`), not the repo's headless screenshot technique - `cacheDisplay` does not capture the Metal layer, so a screenshot "diff" of the treemap compares two blank rectangles and passes no matter what the shader does.

**Instance-rebuild cost lives in COLOUR resolution**, not geometry: directory colours walk their children, so re-resolving every instance cost ~70ms of main thread per style toggle on a real volume scan. `CushionRenderer` caches resolved colours keyed on `(colorGeneration, layoutIdentity)` — the view bumps `colorGeneration` for palette/recency/temporal changes and NOT for style, and `layoutIdentity` bumps on every `cachedLayout` replacement. **Both keys are load-bearing**: keying on rect COUNT instead of identity repaints new rects with the previous layout's colours, which ships as a grey wash over the whole map (that exact bug shipped once). A palette's own `generation` is NOT cross-instance identity: consecutive scans can each construct a different generation-1 palette, so `CushionTreemapView` compares the ranked color assignments and `AppState` keeps its local counter monotonic across reset. Comparing only the counter shipped as a stale prior-volume palette: old extensions stayed colored while new-volume extensions fell back grey. Colours are resolved before any culling decision so every layout index has a cache entry. Card culling must stay SUB-PIXEL (`CardGeometry.minVisibleSide`) — culling visible tiles to buy speed punches folder-colour holes through the map, and the colour cache already bought the speed. **A group of individually sub-pixel siblings is not collectively empty.** `SquarifyLayout` must emit one anonymous aggregate over their visible union; silently dropping them exposed the folder background across 50% of a deterministic equal-byte fixture. Aggregates use a real child only as a unique bookkeeping anchor, expose the owning folder for interaction, receive no filename label, and never render in Cushion.

**Folders (card) style borrows five structural rules from SpaceMonger 1.4** (`seanofw/spacemonger1`, `FolderView.cpp`), and they are the difference between a legible map and confetti: (1) a **subdivide gate** - it only recurses while `w > hmin && h > vmin` (default density row `{32, 24}`, mirrored as `CardGeometry.minSubdivideWidth/Height`), otherwise the folder is ONE block standing in for its contents. DirWiz's layout recurses to a 1pt `minPixelSize`, which is correct for cushions but produces unreadable mush under card decoration, so `CardNesting` collapses below the gate and marks the whole subtree `suppressed`. (2) **Folders uses one depth-colour semantic for the entire map.** SpaceMonger's defaults set both `file_color` and `folder_color` to its eight-entry `BoxColors[depth & 7]`; mixing monochrome folder panels with extension-coloured leaves caused every candidate to share the same abrupt grey-to-red/blue boundary. `FoldersColorScheme` therefore exposes ten numbered complete depth palettes, applied to files, expanded folders, collapsed folders, and density aggregates alike. Cushion and analysis surfaces retain extension colours; the Folders sidebar shows a separate depth key above its still-clickable File Types breakdown. Do not collapse the review to a final palette until Okan chooses on the restored real tree. (3) **Dense sibling groups remain occupied.** When individual members fall below the cutoff, one anonymous aggregate paints their union rather than exposing the parent. (4) SpaceMonger steals pixels from children for the title (`y + 12`, `h - 15`); DirWiz's equivalent is `CardGeometry.headerHeight`. Folder titles own the full usable row width and admit size metadata only through `shouldShowFolderSize`; do not restore intrinsic rounded chips or let size squeeze the name. Any label filter must call `headerHeight(width:height:)` itself, never approximate it - a container between 40 and 56pt tall reserves no strip, and a title drawn there lands on its first child. (5) **Every decorated card owns its contrast, but not every surface needs a bevel.** Classic Bevel retains SpaceMonger's black outer box plus bright top/left and dark bottom/right roles. Crisp and Fine Lines deliberately remain flat; Tinted Frames and Color Headers quiet only expanded-folder chrome. The renderer sets the otherwise-unused card copy of `CushionInstance.coefs.w` to one only for an expanded folder. Cushion MUST keep its real coefficient, and collapsed folders, aggregates, and files keep the zero card marker and exact selected depth colour. Every profile keeps an explicit boundary and measured black-or-white labels. The boundary is shader-only: never inset `displayRects` or `SpatialGrid` to match it. **Edge weight is adaptive by drawn card size** - one backbone shared by all six surfaces (constants mirrored `CardGeometry` ↔ shader, pinned by a mirrored-literal test), because fixed weights failed both ways in native review: thin lines vanished between same-depth siblings (equal colours merge into false slabs) while thick outlines and mid-size bevels turned dense regions to ink. Sub-line tiles (3-7pt) separate via a multiplicative self-shade valley (centres keep the exact depth colour; below 3pt, exact flat fill); reading sizes get a floored-opacity hairline in the card's own darker shade plus a guaranteed 0.45pt background seam; the profile's structural colour/width/opacity blends in over 16-48pt and bevels are admitted only on a 12-32pt ramp. Suppression means hit testing must resolve upward: `visibleAncestor(of:)` walks parents until it finds a drawn node; Folders indexes the post-nesting rects, but never applies the fragment shader's visual gap inset, so card edges remain clickable.

**Overlays and Folders hit testing consume DRAWN geometry, not raw layout geometry.** `updateInstanceBuffer` publishes `onLayoutUpdate(displayRects)` with the post-nesting rects, because Folders insets children via `CardNesting`; labels, selection borders, or hits positioned from `cachedLayout` drift from the tile and collide with the folder title row. Cushion needs no second grid because drawn and layout geometry are identical there. The one deliberate exception is the fragment shader's visual gap: it never changes `displayRects`, so no clickable area is lost. Folder title rows render only in Folders style, where the geometry reserves a header strip for them; cushion children fill their parent edge to edge, so a title there would cover a child.

Tree-table column geometry comes from the shared `TreeTableColumns` constants (TreeRow.swift) - header and rows must consume the same values or columns drift per row.

## Destructive actions

`InstantDuplicateCandidate.id` is derived from its CONTENT (size + name + sorted paths), never a fresh UUID: the living view re-runs instant grouping after every splice, and a random id detaches an already-answered "not duplicates" result from its row. The Duplicates tab is two-tier: `InstantDuplicateFinder` groups by `(size, case-folded name)` purely in memory (no content reads, ~456 ms release for 1M files) and auto-runs on tab open / scan completion / tree mutation, while the exhaustive `DuplicateFinder` content scan stays behind its button. Instant results are `InstantDuplicateCandidate`, a DIFFERENT TYPE from `DuplicateGroup` - every cleanup/trash path takes the latter, so an unverified heuristic result cannot reach deletion; `InstantDuplicateVerifier` (which delegates to `DuplicateContentVerifier.exactGroups`) is the only bridge. Keep that type separation: a `isVerified` boolean would move the guarantee from the compiler to reviewer discipline.

Everything goes to Trash via `TreeActions` → `FileManager.trashItem` - never delete. Duplicate cleanup byte-verifies before trashing (`DuplicateContentVerifier`, opens with `O_NOFOLLOW`) and only proceeds when an unselected byte-identical copy survives. `applyPreset` fails closed: `[]` means "do nothing", and callers must treat it that way. When touching `trashItem` bridging: use the compiler-managed `&nsurlVar` writeback in a synchronous helper - a hand-built `AutoreleasingUnsafeMutablePointer` over strong storage over-releases at pool pop in async contexts (this crashed in production once already; see `performTrash`).

## Temporal snapshots

`SnapshotStore` keeps a per-volume TIMELINE of checkpoints (`DirWiz/Snapshots/v2-<volume-key>/`), replacing the old single `.tdiff` slot that every save overwrote; `DIRWIZ_APP_SUPPORT_DIR` overrides the location (tests), and GUI + CLI (`snapshot`, `snapshot list`, `diff`) share one store per root path. Each checkpoint is the existing `.tdiff` payload inside an LZFSE container (Apple's Compression framework - the zero-dependency rule holds); ~12% of raw, 350k dirs ≈ 2 MB. **The container has a stored-uncompressed mode byte and it is load-bearing**: LZFSE expands small/high-entropy input and `compression_encode_buffer` then returns 0, so without it small snapshots cannot be written at all. **`index.json` is a cache, never the truth** - it is rebuilt from the `.dwcp` files when missing or corrupt, and recovered entries are marked pinned since the store cannot tell which mattered. Anything that lists the store before writing to it must read the index FIRST: `list()` self-heals by adopting every `.dwcp` on disk, so listing after a write re-adopts the file being written. Retention thins unpinned checkpoints (30 dailies / 12 weeklies / 12 monthlies, 500 MB budget) and NEVER evicts a pin. Auto-checkpoints happen on scan completion behind a 6h/1%-growth throttle; the camera action pins.

## Test hygiene: never write to the real defaults

Preferences MUST go through `AppState`'s injected `defaults`, never `UserDefaults.standard` directly - and tests must construct an isolated suite (`UserDefaults(suiteName:)` + `removePersistentDomain`, reusing ONE name rather than a fresh UUID per call, which litters `~/Library/Preferences`). This is not hypothetical: `treemapRenderStyle` and the Insights collapse store originally read/wrote `.standard`, so a test run and a headless screenshot run silently changed the developer's own installed app (it started opening in card style with three Insights sections collapsed). If you add a persisted preference, wire it to `defaults` in `init` and assert in a test that `.standard` is untouched.

## CI is correctness-only; heavy machinery runs locally

Heavy benchmark suites (`PerformanceSensitiveSuites`, `SnapshotStoreSizingTests`) carry `.enabled(if: runHeavyBenchmarks)` (TestHelpers.swift): they run on a local `swift test`, skip automatically when `CI=true` (GitHub Actions always sets it), and `DIRWIZ_HEAVY_TESTS=1/0` forces either way. Rationale: free-plan macOS runners bill at 10x, and a loaded shared runner produces timing numbers this repo has already been burned by twice - so CI asserts correctness (~14s test step) and wall-clock claims are only ever made from local/release runs. A new benchmark or timing gate MUST go under one of the gated suites, not at top level.

## Testing conventions

swift-testing (`import Testing`, `@Suite`/`@Test`/`#expect`/`#require`) - not XCTest. Real-filesystem fixtures via `createTempTree` (Tests/TestHelpers.swift); tree shapes a real scan can't produce are hand-built through `@testable` internals (`setRootPath`/`addNode`/`addChildren`). Tests run in parallel; any suite touching `DIRWIZ_APP_SUPPORT_DIR` (via `withTemporaryAppSupportDir` or inline `setenv`) MUST be declared as `extension AppSupportEnvSuites { @Suite(...) ... }` - `.serialized` on the suite itself is NOT enough (it only orders that suite's own children, not against other top-level suites), and this is the first suspect if CI flakes intermittently. When refactoring an analyzer or scan path, write characterization tests pinning current outputs *before* the refactor (pattern: `Tests/AnalyzerWalkTests.swift`).

**The old `ScanSupervisionTests` flake had three causes, not one.** Instrumented runs showed the preflight helper poisoning with `MustScanSubDirs` even when AppState's later replay was clean. The 40 × 100-file fixture also staged 4,080 items against a 683-item cache and the unchanged 170-item guard, so a test meant to observe a warm patch was silently exercising a cold fallback. Finally, the terminal hardlink assertion sometimes ran while the detached recomputation was still visibly active (`groups=0, running=true`). No capture showed the product bug these tests protect: a stale warm view with empty groups and no recomputation. The fixed tests inject the journal result, use a Phase-A filesystem gate, and wait for the visible hardlink pass before checking its result. A separate injected-`MustScanSubDirs` case proves the app falls back cold with `change journal unavailable` recorded. Do not extend `waitForJournalChanges` or weaken the named assertions. This flake caused three wrong regression investigations (`batched-subtree-splice`, `deferred-ephemeral-roots`, and `retire-root-count-cap`), so future attribution starts from captured replay/decision/progress state and requires the precommitted 14 consecutive green runs. A loaded machine still invalidates timing claims: identical searchfs runs drifted from 26.9 s to 54.6 s on load alone.

**A real FSEvents fixture must wait for the complete mutation shape, not merely one event.** The daemon can journal two independently changed subtrees at different times. `waitForJournalChangesResult(..., until:)` keeps the established 20-second ceiling and exits immediately on poison; pass a predicate that names every area the test later expects. A fixed sleep, or the default any-nonempty predicate when several roots matter, can feed the patcher a valid but incomplete replay and produce a false tree-equivalence failure. Do not extend the timeout.
